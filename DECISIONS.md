# Design decisions

Key decisions made while building this case study, with the alternatives considered. (The case-level design decisions — recommend a blend, branching scenario over video+quiz, converging paths, job aid over memorization, leading+lagging indicators — are documented in the case study itself: [Design decisions](https://iwyusdaz.github.io/should-this-be-a-course/index.html#key-design-decisions).) This file records the *build* decisions.

| # | Decision | Alternatives considered | Rationale |
|---|---|---|---|
| 1 | Write the scenario as Twee source (`src/scenario.twee`) and compile with Tweego CLI | Twine desktop app (GUI); hand-written HTML | Twee is diff-able and version-controllable; the desktop app has no CLI and the build environment is headless. The `.twee` source stays in the repo so a human editor can round-trip it into Twine later. |
| 2 | SugarCube 2.37.3 as story format (pinned) | Harlowe 3 | SugarCube gives direct control over HTML, CSS and JS (needed for the focus-management handler and semantic markup). Version pinned to the story format installed at build time and documented in `scenario-design.md`. |
| 3 | Focus the new passage's heading on `:passagedisplay` | Focus the passage container; aria-live region | Focusing the heading makes screen readers announce the new passage title directly and keeps one obvious reading start point. The container approach announces all passage text but loses the title-first ordering. Implemented with `tabindex="-1"` set programmatically; verified by scripted test. |
| 4 | Converging paths with consequence text driven by choice variables | Fully branching tree (27 leaf paths) | Keeps the story maintainable and readable while still showing consequences; matches the plan's cap of 3 decision points and 3 endings. |
| 5 | Consequence-based feedback (Priya reacts; no "Correct!") | Explicit scoring, "correct/incorrect" labels | The plan (and the evidence base on scenario design) calls for consequences, not judgement labels; also avoids color/redundant-cue accessibility issues. |
| 6 | Survey CSV generated by a seeded script (`scripts/generate-survey.mjs`) | Hand-written CSV; spreadsheet app | Reproducibility: anyone can regenerate the exact file. A fixed seed (20261025) plus documented calibration makes the baseline numbers exact and auditable. The generation method is disclosed in the survey data README. |
| 7 | Charts generated as PNG by a Playwright screenshot of hand-built SVG | Chart.js or another charting library; matplotlib | No extra runtime dependencies; the script renders a plain HTML/SVG table-backed chart and screenshots it. Every chart ships with alt text carrying the takeaway plus a full data table beside it (WCAG 1.1.1). |
| 8 | Job aid PDF produced via Chromium's print-to-PDF with the `tagged` option | LibreOffice; reportlab-style PDF libs | A tagged PDF preserves heading structure for screen readers; Chromium print keeps the HTML as the single source of truth. |
| 9 | Mermaid diagrams with a plain-text summary under each | SVG images with alt text; images only | GitHub renders Mermaid natively in the repo view; the Pages site loads Mermaid from a pinned CDN. Because Mermaid SVGs are not reliably announced by screen readers, every diagram gets a text summary immediately below it. |
| 10 | Just the Docs theme pinned via `remote_theme` to v0.12.0 (latest release at build time) | Default theme; minima; custom CSS | Search, sidebar navigation and accessible defaults out of the box; pinning a release tag keeps Pages builds reproducible. |
| 11 | Agent-based evaluation split into: (a) scripted Playwright tests now, (b) reviewer walkthrough pending, (c) API pipelines pending | Fake "user testing" narrative; skip evaluation | Honesty rules for this portfolio (README disclosure): never present AI or agent work as human testing. The pipelines run only with real API keys and mark everything else PENDING. |
| 12 | Screen-reader evidence via Playwright `ariaSnapshot()` + scripted keyboard tests | Guidepup VoiceOver automation | Guidepup VoiceOver automation does not function on the build machine's macOS version (attempted, documented in the workspace SYSTEM-CHANGES.md). The fallback captures real browser accessibility-tree output, and a manual VoiceOver protocol is provided in `evaluation/human-protocol/` for a human run. No VoiceOver testing is claimed. |
| 13 | Relative `.html` links throughout the Pages site | Absolute URLs; pretty permalinks | Keeps links correct under the `/should-this-be-a-course` baseurl and makes the site verifiable by a link checker before and after publish. |
| 14 | The scenario links back to the job aid at each debrief | Keep the scenario fully self-contained | The debrief explicitly ties the in-story feedback model to the job aid artifact, mirroring the recommended blend (practice + performance support). Relative link works on Pages. |

## Known limitations accepted at build time

- No local Jekyll build (the Pages build is the first real render of the Markdown pages); mitigated by a local relative-link checker (`scripts/check-links.mjs`) and post-publish axe/link/reflow audits.
- Simulated personas cannot demonstrate learning gains; the simulation pipeline is explicitly scoped to finding clarity problems (see `evaluation/METHODS.md`).
